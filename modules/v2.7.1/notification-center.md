# 通知中心

## 1. 模块概述

本模块负责在关键业务节点产生通知，通过飞书机器人推送给相关人员。本期只覆盖**系统自动触发**的事件通知，帮助运营人员及时感知并处理问题。

**业务背景**：当前 PLM推送失败、推送上架失败、发布失败、测价通过等关键业务节点缺乏统一的通知机制，运营人员需手动排查，效率低且容易遗漏。通知中心将这些节点的事件集中处理，通过飞书机器人自动推送。

**本期范围**：
- 仅实现系统事件自动触发的通知（非用户手动发送）
- 通知渠道：飞书机器人（无系统内页面）
- 本期不包含通知列表页、通知详情页等前端页面

**对接关系**：

| 对接系统 | 方向 | 数据/功能 | 说明 |
|---------|------|---------|------|
| 款式管理 | 输入 | PLM推送结果、推送上架结果 | 推送失败产生通知 |
| 现货管理 | 输入 | 推送上架结果 | 推送失败产生通知 |
| 商品管理 | 输入 | 测价结果、撤销测价通过 | 测价通过/撤销时产生通知 |
| 待上架 | 输入 | 审核结果 | 审核驳回时产生通知 |
| ✨ 商品管理（SKC状态） | 输入 | SKC商品状态变更事件 | (v2.7.1 新增) 监听价格申报中/未发布到站点状态，触发有版有样待上架通知 |
| 飞书机器人 | 输出 | 通知消息 | 系统生成的告警/通知推送到指定飞书群或用户 |

## 2. 通知触发规则

### 通知产生条件

| 通知类型 | 触发事件 | 触发来源 | 通知内容 | 接收通知人 |
|---------|---------|---------|---------|---------|
| PLM推送失败 | 款式审核通过后推送PLM失败 | style-management | 款号：{SPU编号}，失败原因：{原因}，失败时间：{时间} | 款式创建人（设计师） |
| 推送上架驳回 | 款式/现货推送到待上架被驳回 | style-management / spot-goods | 款号：{SPU编号}，驳回原因：{原因}，驳回时间：{时间} | 操作推送上架的用户 |
| 发布失败 | 商品发布到Temu失败 | temu-product | 款号：{SPU编号}/{SKC编号}，失败原因：{原因}，失败时间：{时间} | 操作推送上架的用户 |
| 测价通过 | 商品测价标记为通过（手动或系统自动） | temu-product | 款号：{SPU编号}/{SKC编号}，测价通过时间：{时间}，操作人：{操作人} | SKC 对应款式的创建人（设计师） |
| 撤销测价通过 | 运营手动撤销已通过的测价 | temu-product | 款号：{SPU编号}/{SKC编号}，撤销时间：{时间}，撤销操作人：{操作人} | SKC 对应款式的创建人（设计师） |
| ✨ 有版有样待上架 (v2.7.1 新增) | SKC 商品状态变为「价格申报中」或「未发布到站点」，且满足全部前置条件 | temu-product（SKC状态变更事件） | 标题：有待加站商品 / SKC编号：{skc_code} / Temu SKC：{platform_skc_id} / 正文：当前商品已完成核价及审版，请及时加入站点 | SKC 关联款式所属店铺的店铺运营人员 |


### 飞书推送规则

- 所有通知通过飞书机器人发送到对应接收人的飞书会话
- 通知格式：卡片消息，包含通知类型、标题、关键信息（款号、失败原因、时间）

### 用例

##### 用例1：PLM推送失败通知
- **前置条件**：1）PLM推送失败
- **输入**：style-management 调用通知中心接口，传入失败信息
- **业务规则**：生成一条 通知类型=PLM推送失败 的通知，通过飞书机器人发送给接收人
- **后置输出**：接收人在飞书收到通知消息
- **验收标准**：
  - [ ] 飞书消息包含正确的中文款号、失败原因、失败时间
  - [ ] 消息发送到正确的接收人

- **异常处理**：

| 异常场景 | 用户看到的表现 |
|---------|-------------|
| 飞书消息发送失败 | 不影响主业务流程，仅记录日志，支持手动重推 |

##### 用例2：测价通过通知

- **前置条件**：运营手动操作「测价通过」，或 agent 平台写入利润后系统自动标记测价通过
- **输入**：temu-product 调用通知中心接口，传入 SKC 编号、操作人、操作时间
- **业务规则**：生成一条 通知类型=测价通过 的通知，通过飞书机器人发送给该 SKC 对应款式的创建人（设计师）
- **后置输出**：设计师在飞书收到测价通过通知
- **验收标准**：
  - [ ] 飞书消息包含正确的 SPU/SKC 编号、操作人、操作时间
  - [ ] 消息发送到对应款式创建人
  - [ ] 手动操作与系统自动标记两条路径均可触发通知

- **异常处理**：

| 异常场景 | 用户看到的表现 |
|---------|-------------|
| 飞书消息发送失败 | 不影响主业务流程，仅记录日志，支持手动重推 |

##### 用例3：撤销测价通过通知

- **前置条件**：运营在商品列表对 `price_test_passed=true` 且 `disassembly_finished=0` 的 SKC 执行「撤销测价通过」
- **输入**：temu-product 调用通知中心接口，传入 SKC 编号、撤销操作人、撤销时间
- **业务规则**：生成一条 通知类型=撤销测价通过 的通知，通过飞书机器人发送给该 SKC 对应款式的创建人（设计师）
- **后置输出**：设计师在飞书收到撤销测价通过通知
- **验收标准**：
  - [ ] 飞书消息包含正确的 SPU/SKC 编号、撤销操作人、撤销时间
  - [ ] 消息发送到对应款式创建人
  - [ ] 已完成拆版（`disassembly_finished=1`）的 SKC 不触发此通知（无法撤销，源头拦截）

- **异常处理**：

| 异常场景 | 用户看到的表现 |
|---------|-------------|
| 飞书消息发送失败 | 不影响主业务流程，仅记录日志，支持手动重推 |

##### ✨ 用例4：有版有样待上架通知 (v2.7.1 新增)

- **前置条件**：
  1. SKC 项目类型 = 有版有样（`prototype.project_type_name = '有版有样'`）
  2. 样衣审版已完成（`prototype.plm_sample_approved_at IS NOT NULL`）
  3. FOB 核价已完成（`prototype.check_price_state = 2`）
  4. SKC 商品状态变为「价格申报中」（skc_status=7）或「未发布到站点」（skc_status=10）
  5. 该 SKC 尚未通知过（去重检查通过，永久去重）

- **输入**：temu-product SKC 状态变更事件，携带 skc_code、新状态值

- **业务规则**：满足全部前置条件时，查询关联款式信息和店铺运营人员，生成通知并通过飞书机器人发送；写入去重记录

- **后置输出**：店铺运营人员在飞书收到待上架通知

- **验收标准**：
  - [ ] 飞书消息包含正确的 SPU/SKC 编码、商品状态、样衣审版通过时间
  - [ ] 消息发送到正确的店铺运营人员
  - [ ] 同一 SKC 无论状态如何变化，只要通知过一次，后续不再重复通知
  - [ ] 四个前置条件任一不满足时不发送通知

- **去重规则**：
  - 去重维度：SKC（skc_code）
  - 永久去重：同一 SKC 只要通知过一次，无论后续状态如何变化，均不再重复通知
  - 无重置逻辑

- **异常处理**：

| 异常场景 | 用户看到的表现 |
|---------|-------------|
| 飞书消息发送失败 | 不影响主业务流程，仅记录日志，支持手动重推 |
| 关联款式信息查询失败 | 记录日志，跳过本次通知，不影响其他 SKC |
| 去重记录写入失败 | 记录日志；宁可重复通知，不丢失通知 |

---

### ✨ 去重实体：notification_dedup_log (v2.7.1 新增)

| 属性 | 类型 | 必填 | 默认值 | 长度/范围 | 说明 |
|------|------|------|--------|----------|------|
| id | 整数 | 自动 | — | 雪花ID | 主键 |
| notification_type | 短文本 | 是 | — | ≤64字符 | 通知类型标识，如 `pending_listing_notify` |
| biz_key | 短文本 | 是 | — | ≤64字符 | 业务去重键，此场景为 skc_code |
| notified_at | 日期时间 | 自动 | NOW() | — | 通知发送时间 |

**去重判断逻辑**：
1. SKC 状态变为触发状态 → 查询是否存在 `biz_key=skc_code AND notification_type=pending_listing_notify`
2. 存在 → 已通知过，永久跳过
3. 不存在 → 发送通知，写入新记录
