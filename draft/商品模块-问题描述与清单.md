# 商品模块——问题描述与问题清单

## 一、模块背景

系统中款式（Style）与商品（Product）强关联，必须先有款式才能发布商品。模块分三个子模块：

- **款式管理**：管理款式资料（设计款、现货款、组合商品）
- **待上架**：记录款式从审核到发布的过程数据
- **商品管理**：展示和操作已发布到平台的商品

---

## 二、当前完整数据流

```
款式管理
  ├─→ 待上架（新增商品、款式资料更新未发布）
  ├─→ 商品管理（已发布商品复色、款式资料更新已发布、拆版结果）
  ├─→ 商品图片（已发布商品图片更新）
  └─← 商品管理（测价结果反写、平台供货价）

待上架
  └─→ 商品管理（发布商品，首次上架）

商品管理
  ├─→ 待上架（复制商品，触发二次上架）
  └─← 平台（平台同步，外部写入）
```

关键特征：
- 待上架与商品管理之间**双向写入**
- 商品管理同时接受**内部发布**和**平台同步**两条独立写入路径
- 款式管理存在**直连商品管理**的旁路路径（绕过待上架）

---

## 三、现有方案（SDP一款多商品设计文档）

核心方案：新增 `publish_style_spu` / `publish_style_skc` 发布表，将每次发布的过程记录从 `style_on_shelves` 快照表中剥离：

- `style_on_shelves` / `skc_on_shelves` → 降级为首次发布的基础信息快照
- `publish_style_spu` / `publish_style_skc` → 记录每次发布行为（支持同款多店铺、多次上架）
- `product` 表新增 `publish_spu_id` 字段，关联对应的发布记录
- 首次上架：同时写 `style_on_shelves` + `publish_style_spu`
- 二次上架（从商品列表复制）：只写 `publish_style_spu`

---

## 四、问题清单

### P0 — 结构性问题（影响后续所有改动）

**[问题1] 待上架与商品管理的循环依赖未解开**

现有方案中，二次上架仍需经过以下路径：

```
商品管理 → 生成 StyleOnShelves 中间对象 → 生成 publish_style_spu
```

`style_on_shelves` 仍是二次上架的必经中间层，商品→待上架→商品的双向依赖并未消除，只是在其上加了一层转换。根本耦合点未动。

**[问题2] `style_on_shelves` 在新方案中的生命周期和职责未定义**

文档说它是"基础信息表"，但未回答：
- 首次上架写入后，它后续是否还被更新？
- 二次上架是否写入它？
- 它与 `publish_style_spu` 的字段如何分工？

这个问题不澄清，首次和二次上架的代码实现会走向不一致。

---

### P1 — 数据一致性问题（影响数据可信度）

**[问题3] 平台同步 vs 内部发布的字段覆盖规则缺失**

商品数据有两条写入路径：
- 路径A：内部发布（款式 → 待上架 → 商品）
- 路径B：平台同步（平台 → 商品）

两条路径操作同一条 `product` 记录，但文档中没有定义：
- 哪些字段由内部维护，哪些字段由平台维护？
- 平台同步时是否会覆盖内部写入的字段？

每次平台同步都有潜在的数据污染风险。

**[问题4] `product.publish_spu_id` 的更新规则不明确**

一款商品可以经历多次上架（`on_shelves_times` 字段证明了这一点），但 `product.publish_spu_id` 是单值字段：
- 它指向最新一次发布记录，还是首次发布记录？
- 平台同步更新商品时，这个字段会被覆盖吗？
- 二次上架发布完成后，这个字段如何更新？

---

### P2 — 迁移风险（影响上线质量）

**[问题5] 历史数据迁移语义不匹配**

迁移方案是直接复制 `style_on_shelves` → `publish_style_spu`，但两张表语义不同：
- `style_on_shelves`：首次发布快照
- `publish_style_spu`：每次发布的行为记录

直接复制后：
- 历史记录的 `on_shelves_times` 无法确定，默认值不明
- `on_shelves_tag`（首次/二次标签）对历史数据无法准确标注
- `secondary_reason_code` 字段历史数据全为空，逻辑上应标记为首次上架
